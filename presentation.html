Problem — co chcemy rozwiązać?

Każda zmiana w CSS, szablonie lub bibliotece ikon może niezauważalnie zmienić wygląd komponentu.

  • Code review nie wychwytuje zmian wizualnych
  • Testy jednostkowe / e2e sprawdzają zachowanie, nie wygląd
  • Ręczne przeglądanie każdej story po każdym PR jest nieefektywne
  • Regresje wykrywane dopiero na produkcji

Przykładowe regresje

  • Zmiana padding w tokenie design systemu
  • Upgrade biblioteki ikon → inny rozmiar SVG
  • Nadpisanie font-family przez globalny styl
  • Zmiana wersji Angular Material
  • Refactor SCSS → niezamierzona zmiana specificity

Podejście 1 — kod testu

visual-tests/storycap.test.ts

import { configureToMatchImageSnapshot }
  from 'jest-image-snapshot';
import * as fs from 'fs';
import * as path from 'path';

const toMatchImageSnapshot =
  configureToMatchImageSnapshot({
    customSnapshotsDir:
      '__screenshots_baseline__',
    failureThreshold: 0.02,        // 2%
    failureThresholdType: 'percent',
  });

expect.extend({ toMatchImageSnapshot });

describe('Button component', () => {
  it('Primary button matches baseline', () => {
    const png = fs.readFileSync(
      '__screenshots__/Components_Button_Primary.png'
    );
    (expect(png) as any)
      .toMatchImageSnapshot({
        customSnapshotIdentifier:
          'button-primary',
      });
  });
});

Podejście 2 — kod testu

e2e/visual/button.visual.spec.ts

import { test, expect, Page }
  from '@playwright/test';

async function gotoStory(
  page: Page,
  storyId: string
): Promise<void> {
  await page.goto(
    `/iframe.html?id=${storyId}&viewMode=story`
  );
  await page.waitForLoadState(
    'domcontentloaded'
  );
  await page.waitForSelector(
    'app-button', { state: 'visible' }
  );
  await page.waitForTimeout(300);
}

test.describe('Button – visual', () => {
  test.use({ viewport: {
    width: 400, height: 200
  }});

  test('Primary button', async ({ page }) => {
    await gotoStory(
      page, 'components-button--primary'
    );
    await expect(page)
      .toHaveScreenshot('button-primary.png');
  });
});

playwright.config.ts (fragment)

export default defineConfig({
  testDir: './e2e',
  use: {
    baseURL: 'http://localhost:6006',
    viewport: { width: 1280, height: 720 },
  },
  expect: {
    toHaveScreenshot: {
      maxDiffPixelRatio: 0.01,  // 1%
      threshold: 0.1,
    },
  },
  snapshotDir: '__snapshots__',
  webServer: {
    command: 'npm run storybook',
    url: 'http://localhost:6006',
    reuseExistingServer: true,
  },
});

Podejście 3 — zalety i wady

✅ Zalety

  • UI Review — reviewer zatwierdza zmiany wizualne w przeglądarce, jak code review ale dla wyglądu
  • Zero konfiguracji — automatycznie wykrywa wszystkie stories, bez pisania testów
  • Historia buildów — pełna historia snapshotów per branch i commit
  • Natywna integracja z GitHub/GitLab — PR check "UI Tests" blokuje merge do zatwierdzenia
  • TurboSnap — testuje tylko komponenty których pliki zmieniły się w PR (szybciej)
  • Renderowanie w chmurze — spójne wyniki niezależnie od OS dewelopera

  • Płatne powyżej 5000 snapshotów/miesiąc — przy dużym teamie i wielu PR może być kosztowne
  • Screenshoty i kod komponentów trafiają do zewnętrznego serwera (kwestia polityki bezpieczeństwa)
  • Wymaga dostępu do internetu — nie działa w pełni offline/air-gapped
  • Mniejsza kontrola nad środowiskiem renderowania vs lokalne narzędzia
  • Konto i token wymagane do startu — próg wejścia wyższy niż Playwright

Podejście 3 — co Chromatic daje zespołowi?

👥
UI Review — wspólna decyzja, nie tylko "test padł"
Każda zmiana wizualna w PRze trafia do przeglądarki jako osobny widok. Reviewer widzi stary wygląd, nowy wygląd i diff. Klika Accept albo Deny. Merge nie przejdzie dopóki ktoś tego nie zatwierdzi — dokładnie jak code review, ale dla pikseli.
✍️
Zero testów do pisania
Chromatic sam wykrywa wszystkie stories ze Storybooka. Dodajesz nowy komponent, piszesz story — automatycznie jest objęty testami wizualnymi. Nie musisz pamiętać żeby dodać go do żadnego pliku testowego.
🕐
Historia buildów
Każdy build jest zachowany. Możesz wrócić do dowolnego commita i zobaczyć jak wyglądał komponent w tamtym momencie. Przy Playwrighcie masz baseline'y w repo — ale nie masz takiej nawigacji.
⚡
TurboSnap — testuje tylko to co się zmieniło
Chromatic analizuje które pliki zmieniły się w PRze i testuje tylko powiązane stories. Na dużym projekcie to robi ogromną różnicę w czasie buildu.
📦
Snapshoty w chmurze — nie w repozytorium
Przy dużym design systemie z setkami komponentów baseline'y PNG mogą ważyć dziesiątki megabajtów. U Chromatic tego w repo nie ma.

Chromatic — czy można hostować we własnej infrastrukturze?

☁️ Chromatic Cloud (domyślny)

  • Kod i snapshoty trafiają na serwery Chromatic
  • Wymaga dostępu do internetu
  • Free do 5 000 snap/mies. · płatne powyżej
  • Gotowe natychmiast — zero DevOps

🏢 Chromatic On-Premises (Enterprise)

  • Pełne Chromatic na własnych serwerach
  • Kod i snapshoty nie opuszczają infrastruktury
  • Działa w środowiskach air-gapped (bez internetu)
  • Wymaga kontaktu z Chromatic i planu Enterprise

Open-source, działa lokalnie lub na własnym CI. Podobny przepływ do Chromatic. GitHub: lost-pixel/lost-pixel

Rekomendacja dla organizacji z restrykcyjną polityką bezpieczeństwa: Playwright (lokalnie) + Lost Pixel lub reg-suit (CI) — zero zależności od chmury zewnętrznej

reg-suit + S3 — jak skonfigurować własną review UI

1. Instalacja pluginu

npm install --save-dev reg-publish-s3-plugin

2. regconfig.json

{
  "core": {
    "addonModules": [
      "reg-keygen-git-hash-plugin",
      "reg-publish-s3-plugin"
    ]
  },
  "plugins": {
    "reg-publish-s3-plugin": {
      "bucketName": "nasz-bucket-reg-suit"
    }
  }
}

3. Uruchomienie — bez zmian

npm run test:visual:reg-suit

4. AWS — skąd wziąć dostęp

IAM Console → Users → Create access key (typ CLI) → AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY. W CI lepiej: OIDC + IAM Role, bez zapisywania sekretów.

5. Bucket S3 + uprawnienia

aws s3 mb s3://nasz-bucket-reg-suit \
  --region eu-central-1
{
  "Effect": "Allow",
  "Action": ["s3:PutObject","s3:GetObject","s3:ListBucket"],
  "Resource": ["arn:aws:s3:::nasz-bucket-reg-suit/*"]
}

💡 Kreator npx reg-suit prepare potrafi założyć bucket i wygenerować config automatycznie.

Co dostajemy: raport HTML z diffami wrzucany na nasz S3 po każdym runie, link wypisywany w terminalu/CI (opcjonalnie jako komentarz na PR przez reg-notify-github-plugin). Bucket i dane cały czas w naszej infrastrukturze — zero SaaS.

Podejście 4 — druga ścieżka: Argos bez Storycap

Odkryte i przetestowane live w tej sesji — koryguje wcześniejsze założenie "Argos zawsze wymaga zewnętrznego capture"

1. Pakiet @argos-ci/storybook + Vitest browser mode (@storybook/addon-vitest) — auto-discovery story, bez Storycap
2. Warunek: Storybook musi stać na builderze Vite, nie webpack. Nasz projekt (Angular) domyślnie używał webpacka — trzeba było zmigrować na @storybook/angular-vite
3. Ta migracja wymaga Angular 21+ — u nas spełnione, ale to nie jest opcja dla starszych projektów Angularowych ani innych frameworków bez Vite-buildera
4. Efekt: CI=true ARGOS_TOKEN=... npx vitest run --project=storybook — jedna komenda, zero Storycap, build wysłany do Argos
// vitest.config.ts
import { storybookTest } from '@storybook/addon-vitest/vitest-plugin';
import { argosVitestPlugin } from '@argos-ci/storybook/vitest-plugin';

plugins: [
  storybookTest({ configDir: '.storybook' }),
  argosVitestPlugin({ uploadToArgos: !!process.env.CI }),
]
Pułapki, na które trafiliśmy live: wersja @storybook/addon-vitest musi dokładnie pasować do wersji storybook (inaczej błąd importu); brakujący peer dependency @angular/animations; a po migracji ze Storycap na Vitest Argos zresetował baseline — inny schemat nazw screenshotów = wszystko widziane jako "28 added + 28 removed", nie "changed".

Podejście 4 — live demo: dlaczego niektóre buildy są "auto-approved"?

Realny upload z tego repo do Argos — dwa buildy, ten sam kod, różny wynik

main → main (build #7)

  • Upload bezpośrednio na branchu bazowym
  • github.state: success
  • opis: "automatically approved"
  • brak PR-a → nie ma czego blokować, build staje się nowym baseline'em

demo/regresja-paddingu → main (build #9)

  • Upload z osobnego brancha, referencja jawnie do main
  • github.state: failure
  • opis: "7 changed — waiting for your decision"
  • w realnym repo: blokuje merge PR-a do czasu ręcznej recenzji

Odpowiedź z API Argos (argos build get --json)

"notification": {
  "description": "7 changed — waiting for your decision",
  "github": { "state": "failure" }
}
Wniosek: Argos auto-zatwierdza tylko wtedy, gdy head.branch == base.branch — czyli push bezpośrednio na main. Prawdziwa recenzja (blokująca merge) pojawia się tylko dla builda z osobnego brancha porównanego z main. Approve/reject z CLI (argos review create) wymaga osobnego personal access tokena — token repo (CI) może tylko wysyłać i czytać, nie zatwierdzać.

Podejście 4 — zalety i wady

✅ Zalety

  • UI Review w chmurze — zatwierdzanie/odrzucanie zmian wizualnie, tak jak w Chromatic
  • Niezależne od źródła screenshotów — działa z Storycap, Playwright, Cypress, dowolnym narzędziem generującym PNG
  • Zarządzanie flaky testami — argos change pozwala oznaczyć zmianę jako flaky, żeby nie failowała kolejnych buildów
  • Równoległe buildy — --parallel łączy sharded runy CI w jeden build
  • Konfigurowalny próg czułości diffa per upload (--threshold)
  • Snapshoty trzymane w chmurze — nie zaśmiecają repozytorium

⚠️ Wady

  • Zero-config tylko warunkowo — natywna integracja (bez Storycap) wymaga Storybooka na builderze Vite; bez tego dziedziczy ograniczenia Storycap (Chromium only, brak play functions)
  • Dwa narzędzia do utrzymania zamiast jednego (capture + upload) — więcej ruchomych części w CI
  • Screenshoty i metadane trafiają do zewnętrznego serwera — ta sama kwestia bezpieczeństwa co przy Chromatic
  • Mniejszy ekosystem i społeczność niż Chromatic (który jest ściśle zintegrowany ze Storybookiem)
  • Konto i token wymagane do startu

Argos vs Chromatic — bezpośrednie porównanie

Kryterium 🟢 Chromatic 🟠 Argos
Renderowanie story Sam renderuje w chmurze (własne przeglądarki) Storycap (uniwersalnie) lub natywnie przez Vitest — tylko na builderze Vite
Optymalizacja kosztów TurboSnap — renderuje tylko story dotknięte zmianą (−75–90%) Brak takiego mechanizmu — płacisz za każdy wysłany screenshot
Integracja ze Storybookiem Najgłębsza — twórcy Storybooka, dedykowany addon w UI Dobra, ale wymaga capture albo migracji buildera na Vite
Cena (free / Pro) 5k/mies. free · $149/mies. za 35k 5k/mies. free na zawsze · $100/mies. za 35k
Elastyczność źródła screenshotów Tylko Storybook Dowolne: Storycap, Playwright, Cypress, natywny Vitest
Auto-approve buildów Nie sprawdzaliśmy live w tej sesji Tak, warunkowo — push na main auto-zatwierdza się (brak PR-a do zablokowania)

⚠️ Co się stało w naszym live demo

Upload 28 story regularnie zawieszał się na etapie asset-discovery ("wait for network idle") — proces żył (aktywne procesy Chromium), ale bez postępu przez kilka-kilkanaście minut.

Próby: (1) domyślny timeout — brak wyniku po ~18 min; (2) flaga --network-idle-timeout odrzucona przez walidację CLI (limit 750ms) i wprowadziła proces w gorszy stan; (3) sama zmienna PERCY_NETWORK_IDLE_WAIT_TIMEOUT — nadal bez zakończenia po kilku minutach.

Nie wiemy, czy to specyfika naszego środowiska (jakiś zasób w Storybooku, który nigdy nie osiąga "network idle") czy szerszy problem SDK — ale to realne ryzyko wdrożeniowe warte zweryfikowania przed decyzją, nie tylko punkt z dokumentacji
